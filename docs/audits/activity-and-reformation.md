# 活动与装备改造审计

状态：进行中

## 活动计时器

旧版将八类活动历史直接打包在前端代码中，并重复实现开始日期、结束日期、持续天数和间隔天数计算。新版按已确认方案改为 GitHub 公共资料更新。

### 已确认问题

- 活动数据与程序代码耦合，更新一条日期也必须重新发布客户端。
- 八类活动使用大量重复计算代码，容易出现分支不一致。
- 部分条件使用 `date > start || date < start`，除日期刚好相等外始终成立，表达明显错误。
- 直接依赖 `Date.parse()`，没有明确“仅日期”与“具体时间”的时区语义。
- 活动处于进行期时，部分“距开始时间”结果被置为零，字段含义不稳定。

### 新版处理

- 公共数据使用明确的 `YYYY-MM-DD` 日期或带时区的完整时间，禁止混用。
- 仅日期计算统一转换为 UTC 日序号，不受 Windows 时区和夏令时影响。
- 活动状态明确分为 upcoming、active 和 ended。
- 持续天数按首尾日期都计入；无结束日期的活动使用独立类型表示。
- 数据更新必须通过开始/结束顺序、重叠、重复 ID 和日期合法性校验。

核心包已加入跨闰日、边界日期和非法日期测试。

## 装备改造

旧版装备改造按四条工艺等级之和计算阶段消耗。当前页面明确说明使用最坏情况，即不考虑约 0.4%～0.5% 的改造暴击。

旧版区间汇总行为：

```text
重构分子总量 = Σ 每阶段“含工艺提升”的重构分子
纳米 3 总量 = Σ 每阶段“含工艺提升”的纳米 3
金条总量 = Σ 每阶段“含工艺提升”的金条
点击次数 = Σ (阶段保底进度 + 1 次晋级点击)
```

### 数据风险

- 原始资料来源时间为 2022-08-12 至 2023-06-30，可能已经过时。
- 旧版说明明确承认早期部分进度次数不确定。
- 纳米 3 到金条的换算使用 0.19，系统直购对比使用 0.125，必须作为版本化规则而非常量散落在页面。
- 页面只计算武器、护甲、头盔中的一类，旧版提示均衡提升时由用户自行乘 3，容易误解。

新版会保留“最坏情况”作为清晰命名的保守估计，并在数据包中标注规则来源、适用版本和置信状态。不会把估算条目伪装成已验证数据。
